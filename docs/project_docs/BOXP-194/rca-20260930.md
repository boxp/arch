# BOXP-194 control-plane/API/etcd RCA（読み取り専用）

## 結論と範囲

CP3の障害時に数十秒のetcd apply遅延があり、API/kubelet疎通失敗・lease停止と同じ障害期間に重なる。ホストまたはetcd処理経路の一時停止が有力な調査対象だが、ディスク、CPU、ネットワークのどれが原因かは未確定。CP2の先行apiserver再起動と同一原因かも断定できない。

05:28以降の観測では直接API・etcd health・全7台Readyは復帰している。ただしCP1には現在も遅延の兆候があり、全体の収束を宣言しない。04:15/04:39の指示に従って更新を再開せず、調査成果のみReviewへ提出する。

対象コードbaseはarch main `0bd31d60a`。旧更新準備[PR #12990](https://github.com/boxp/arch/pull/12990)のruntime変更は取り込まない。今回の変更は本計画・RCA・匿名化した集計証跡のみ。snapshot/restore、dry-run、dispatchを含む本番変更なし。

## 現在の観測と証拠の限界

機密情報を除いた数値とPod状態は[集計証跡](rca-observation-20260930.json)に保存した。接続情報・ログ本文・Secret・kubeconfig内容は保存していない。既存admin kubeconfigを許可済みホスト上で使用し、etcd healthだけ既存Podでexecした。etcd member/data/configの変更なし。

3CPのkubelet/CRI-Oはactive、systemd NRestarts=0、起動時刻は8月のまま。CP3ホストuptimeは約41日。今回取得したuptimeとサービス状態は、障害期間を挟むホストrebootやkubelet/CRI-Oサービス再起動を支持しない。apiserver restartはCP1=75、CP2=48、CP3=60。CP3の最後の終了は04:29:49だった。

現在3CPのrootとetcd dataのfilesystemは同じmmcデバイスで、使用率CP1=34%、CP2=21%、CP3=26%。現在available memoryは約1016/964/1618MiB。現在のディスク満杯・MemoryPressureは観測されないが、障害時の一時的なIO/メモリ停滞を除外しない。

短いvmstat区間ではCP1のCPU idleは12–21%、CP2は48–82%、CP3は76–91%。全CPは4CPU。収集コマンドやkubectl自体もCPUを使用し、psの%CPUは瞬時使用率ではないので、障害時のCPU飽和をこの値から推定しない。

journalctl kernelの指定区間はNo entries。dmesg末尾300行のOOM/IO error/stallパターン一致は0だが、ログ全履歴を保証しない。PSIは取得できず、CPU/IO/memory pressureの直接比較は未達。ログローテーションによりetcdログの保持開始はmemberごとに異なり、warning件数をmember間で比較しない。CP3の現在apiserverログは再起動前の障害区間を含まない。

## etcd metricsの短区間差分

05:29:23頃と05:30:14頃に既存metricsを取得。各memberの取得時刻は完全同時ではない。累積カウンタを差分化し、count減少はなく、leader changes/proposals failedの増分は3CPとも0。peer RTTのラベルは除去し、この短区間だけでは障害時の特定peer経路を評価しない。

ホストreboot、kubelet/CRI-Oサービス再起動、現在の容量枯渇は今回の状態から支持されない。OOM、etcd quorum喪失/data破損、dry-runが障害原因という仮説は裏付け未取得で、断定しない。package更新は障害前後とも本票では未実施なので、候補patchを導入した結果の障害ではない。読み取りや事前検証の負荷が寄与した可能性までは除外しない。

## 次の観測と安全条件

次回は新しい設定や高負荷benchmarkを加えず、既存監視で障害時刻のWAL/backend histogram、peer RTT/leader/proposal、CPU/IO/device await、Node lease、直接API/VIPを同じUTC軸へ照合する。データが残っていなければ、許可済みの低頻度read-only観測で再発時の値を取得し、失敗も記録する。probe失敗とcontainer終了の因果確認には、保持されている既存kubeletイベント/前containerログを限定して集計する。

現在の症状非再現だけで自動runnerを起動しない。復旧変更やKubernetes更新の再開にはユーザーの明示指示が必要。再開判断では直接APIとetcd health、Node lease/Ready、Longhornに新規/悪化がなく、障害が再発しない観測を確認する。metrics warning単体を新しい一律必須gateにせず、API/etcd/Nodeの機能失敗と同時刻の傾向を評価する。

現時点では具体的な修正操作を選べる根因証拠が不足するため、rebootやetcd操作は提案しない。将来の変更案は対象/根拠/影響/停止条件/rollbackを別途記録し、承認前に実行しない。更新を明示的に再開する場合のみ、実施直前snapshotと隔離restore経路など03:11の復旧要件を更新計画として再確認する。本RCAでは実行しない。
