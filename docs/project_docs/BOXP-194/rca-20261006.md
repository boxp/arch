# BOXP-194 control-plane不安定 RCA 第2報（2026-10-06、読み取り専用）

## 結論

lolice control-plane（CP1〜CP3、各4CPU / 3.9GiB RAM / eMMC、swapなし）では、**kube-apiserverの常駐メモリ（WSS約2.0〜2.6GiB）がノード物理メモリを圧迫し、MemAvailableが約200〜300MiBまで落ちた時点でページキャッシュの追い出しとmajor page fault（85〜250回/秒）が発生し、同一eMMC上のetcd WAL fsync / backend commitとapiserver自身が停止する**という連鎖が、観測可能な全てのleader change / apiserver再起動イベントに共通している。apiserverはliveness probe失敗でkubeletにSIGKILL（exit 137）され、メモリが解放されて回復する。2026-09-30のCP2 restart、CP3 readyz HTTP 500、CP3 NotReady、KV/Range DeadlineExceeded、数十秒のetcd applyも、この連鎖と整合する（当時のCP2はprobe失敗→Killingを前回RCAで確認済み。CP3の再起動を引き起こしたprobeイベント自体は当時も今回も直接確認できておらず、CP3についてはmetrics上の同時刻のメモリ逼迫・major faultから推定した整合解釈に留まる）。

この状態は少なくとも2026-09-06（Prometheus保持範囲の先頭）から継続する慢性状態であり、Kubernetes 1.36 patch更新の準備作業やpackage変更は原因ではない（更新は一度も実施していない）。ただし2026-09-29以降にイベント頻度が明確に悪化しており、同時期に増えたcontrol-plane向け読み取り負荷（Task Board agentによるAPI観測を含む）が、余裕のないメモリ状態の引き金になった可能性は除外できない。

確度: 連鎖の機序（メモリ逼迫→major fault→IO/etcd停滞→probe失敗→SIGKILL→leader change）は**高**。09-29以降の悪化トリガーの特定は**中〜低**（audit logがなくクライアント別の要求量を切り分けられない）。

本RCAは読み取り専用で実施した。update/drain/Apply、reboot、Pod/Node削除、etcd member操作、restore、manifest変更、Argo sync、Secret参照はしていない。

## 証拠の取得方法と限界

- Kubernetes API GET（Node/Lease/Pod/Event/CronJob/CRD/Longhorn/Argo CD Application）。
- 許可済みSSH（TCP/22）から各CPのkubelet/kernel journalをパターン件数のみ集計。raw logは転記しない。
- monitoring namespaceのPrometheus（保持31日）に対し、CP1上のadmin kubeconfig経由でPrometheus Pod内のpromtoolを実行し、集計値のみ取得した。Prometheus ServiceはCodex Podからも、apiserver proxy経由でも到達できなかった（NetworkPolicy 8件が存在）。
- etcd Podへのexecはetcdctl endpoint status / healthの読み取りのみ。
- 制限: audit logなし。apiserver metricsにクライアント識別子がなく、負荷源はverb/resource単位でしか見えない。CRI-Oのcontainer log上限が1MiBでetcd/apiserverのcontainer logは直近数十分〜1時間しか残らない。kernel PSI（/proc/pressure）は無効で、CPU/IO/memory stallを直接比較できない。node_exporterのscrapeが停止した5分バケットは「*」付きで前バケットの値を使った。
- 本調査自体のGET/LIST（全Pod JSON、全CRD JSON等）もapiserver負荷になる。観測回数は最小限にしたが、ゼロではない。

- 3CPのsystem / softirq CPU比率は最大でも0.11 / 0.05で、割り込みやネットワーク処理の飽和はない。NICのrx errorは0。NIC dropは10-02以降にCP1で最大70回/秒出ているが、leader changeバケットとの一致は限定的で、二次的影響と判断する。

## 根本原因の整理

以下は観測事実（metrics・journal件数・API状態）と整合する解釈であり、PSI・audit log・障害時のプロセス別統計を欠くため、確度を付して記す。個別イベントの因果を機械的に証明したものではない。

1. **構造要因（確度 高）**: 3.9GiB RAM・swapなしのCPで、kube-apiserverのWSSが2GiB超に達する。kubeadm既定でapiserverにはmemory limit / requestがなく、kubeletのeviction thresholdは既定（memory.available 100Mi）で、ページキャッシュを使い切った後にしか動作しない。この構成ではMemAvailable 200〜300MiBで常時運用され、わずかなスパイクでmajor faultの嵐が始まる。
2. **増幅要因（確度 中）**: etcd dataとrootfs（バイナリ・ライブラリ）が同一eMMC上にあり、major faultの読み戻しとWAL fsyncが同じデバイスで競合する。CP1は他2台よりfsyncが約3倍遅い。
3. **恒常負荷（確度 中）**: CRDへのServer-Side Apply約45回/分とCRD GET約90回/分、Argo CD Application PATCH約49回/分、Calico policy LIST群が、apiserverのwatch cache / 変換バッファのメモリを高止まりさせている。
4. **09-29以降の悪化トリガー（確度 中〜低）**: 同時期にTask Board agentのCPU使用（API観測）が約5〜8倍、WATCH開始とpods LISTが増加し、429が07時台に集中して発生した。クライアント別のaudit logがないため、「どのクライアントの要求が引き金か」は断定しない。

## 復旧・再開の安全条件（提案、未実施）

以下は提案であり、本runでは何も変更していない。実施にはユーザーの明示指示が必要で、各項目は対象・影響・停止条件・rollbackを別途記録したうえで1台ずつ行う。

1. **apiserverのメモリ圧迫を下げる**（効果 大、リスク 中）。候補: kube-apiserverの`--watch-cache-sizes` / `--default-watch-cache-size`縮小、`--target-ram-mb`の明示、またはstatic Pod manifestへのmemory requestsとkubelet `systemReserved` / `evictionHard`の引き上げ。manifest変更はkubeadm管理ファイルの直接編集になるため、Ansible role経由で管理し、1 CPずつ適用して1時間観測する。
2. **恒常負荷の削減**（効果 中、リスク 低）。Argo CDのCRDを含むApplicationの再同期間隔延長またはServer-Side Diff / Apply対象の見直し、Calico policy LISTの発生源確認、TiDB / PD CrashLoopの停止または隔離。いずれもcontrol-planeの外側の変更で、rollbackが容易。
3. **観測負荷の抑制**（即時、リスクなし）。Task Board agentやRCA観測での全namespace Pod / 全CRD JSON取得を避け、必要なら`kubectl get --raw /metrics`やPrometheusの集計値を使う。本RCAも同じ制約を次回から適用する。
4. **swap / zramの有無の確認**（効果 中、リスク 低〜中）。Armbianのzramデバイスが3つ存在するがswapは0。kubeletのswap設定との整合を確認したうえで、少量のzram swapが回収停滞を緩和するかを別途検討する。kubelet既定（NoSwap）との組み合わせ検討が必要で、本RCAでは推奨しない。
5. **Kubernetes 1.36 patch更新の再開条件**。上記1または2の実施後に、leader change 0〜1回/日、apiserver再起動0回/日、MemAvailable日最小500MiB以上が連続3日以上続いたことをPrometheusで確認する。現状（当日4イベント、2〜4時間おき）ではdrain / 再起動を含む更新手順の最中にapiserver停止が重なる確率が高く、再開を推奨しない。
6. **残骸Podの削除**（任意、リスクなし）。default namespaceの`node-debugger-*` 5件はPhase=Failedで無害だが、明示指示があれば削除する。
