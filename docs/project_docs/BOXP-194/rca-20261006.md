# BOXP-194 control-plane不安定 RCA 第2報（2026-10-06、読み取り専用）

## 結論

### 観測事実（確度 高）

- lolice control-plane（CP1〜CP3、各4CPU / 3.9GiB RAM / eMMC、swapなし）では、kube-apiserverの常駐メモリ（WSS約1.8〜2.6GiB）が物理メモリの半分以上を占め、MemAvailableが日最小で約200〜320MiBまで落ちる状態が、少なくとも2026-09-06（Prometheus保持範囲の先頭）から継続している。
- 集計期間（2026-09-29 00:00〜10-06 05:15 UTC、7日5時間15分。以下「集計期間」。初版と改訂1で「7日間」と表記したが実範囲はこの通り）で、etcd leader changeが記録された5分バケットは46件ある。このうち42件（91%）では、少なくとも1台のCPがバケット終端の15分前〜10分後の照合窓内に「MemAvailable 512MiB未満 かつ major page fault 50回/秒超」（以下「メモリ逼迫」）を示した。同じ条件を集計期間の全5分バケットで見ると、leader change窓の外では各CPで0.5〜0.8%しか発生しない。leader change窓内では3.4〜8.5%で、約7〜12倍に濃縮されている。ただしこの照合窓は終端後10分を含むため、この42件は**照合窓内の相関**であり、逼迫がleader changeに先行したことを示す値ではない。
- 先行区間だけで再集計すると（本改訂で追加、後述）、バケット開始前（終端15分前〜5分前）に限ってもいずれかのCPがメモリ逼迫を示したのは46件中25件（54%）で、平常時比で約3〜12倍に濃縮される。残り21件の内訳は、照合窓内では逼迫が同一バケット内または直後にだけ観測された17件（因果の向きを判別できない）と、照合窓内でも逼迫を検出できなかった4件（上記E分類、未説明）である。
- 一方、同じ46件のうちkube-apiserverの再起動（exit 137）を伴うものは22件（48%）で、再起動したCPとメモリ逼迫を示したCPが一致するのは12件（26%）に留まる。残り20件（43%）はapiserver再起動なしでメモリ逼迫とetcd slow applyの急増だけが観測され、4件（9%）は上記しきい値ではメモリ逼迫も再起動も検出されなかった。
- 集計期間のapiserver再起動25バケット（CP1 9 / CP2 8 / CP3 8）のうち、leader changeバケットの照合窓（終端15分前〜10分後）に入るのは14件で、11件はleader changeを伴わない。この14件は再起動バケット側から数えた値で、前項の22件はleader changeバケット側から「終端5分前〜15分後に再起動があったか」を数えた値である。1回の停滞エピソードが複数バケットにまたがるため両者は一致しない。10-06当日の03:05（CP3）と03:39（CP1）のexit 137もleader changeを起こしていない。

### 解釈（仮説）

- **メモリ逼迫→ページキャッシュ追い出し→同一eMMC上のetcd WAL fsync / apply停滞→heartbeat / proposal失敗→leader change**という連鎖は、leader changeの主要な機序の候補として**確度 中**と評価する（改訂1の「中〜高」から引き下げ）。根拠は、照合窓内で46件中42件が一致すること、先行区間だけに限っても46件中25件（54%）で逼迫が先行し平常時比約3〜12倍に濃縮されることである。一方で、残り21件のうち17件では逼迫がleader changeと同一バケット内または直後にしか観測されず（4件は照合窓内でも未検出）、**leader changeの結果として起きた逼迫・slow apply**（leader交代に伴うapiserverのwatch再接続・relistによる一時的なメモリ増）を原因側に数えている可能性を排除できない。相関に基づく推定であり、PSI・障害時のプロセス別統計がないため個別イベントの因果を証明したものではない。厳密先行で本仮説が支持されないのは21件（17件は因果の向きが不明、4件は照合窓内でも逼迫未検出）で、未検出の4件については別要因（短時間のCPU飽和、ネットワーク、しきい値未満の停滞）を排除していない。
- **apiserverのliveness失敗→SIGKILL（exit 137）**は、メモリ逼迫を共通要因とする解釈と整合する並行症状であり（共通原因は仮説で、因果は未確定）、leader changeの必要条件ではない（**確度 高**で「必要条件ではない」と言える）。第2報初版では「全イベントに共通する連鎖の一部」としていたが、イベント単位の照合で撤回する。apiserver再起動後にWSSが約0.7〜1.0GiBへ落ちてMemAvailableが回復するのは事実だが、それは結果であり原因ではない。
- 2026-09-30のCP2 restart、CP3 readyz HTTP 500、CP3 NotReady、KV/Range DeadlineExceeded、数十秒のetcd applyは、09-30 03:00〜03:20（CP1再起動・CP3逼迫）および04:20〜04:25（CP3逼迫・CP3 scrape欠落）のバケットとして今回の表に現れており、上記仮説と整合する。CP3の再起動を引き起こしたprobeイベント自体は当時も今回も直接確認できていない。
- 09-29以降にleader change / 再起動頻度が明確に悪化したこと（0〜7/日→8〜18/日）の引き金は**確度 中〜低**。audit logがなく、クライアント別の要求量を切り分けられない。

本RCAは読み取り専用で実施した。update/drain/Apply、reboot、Pod/Node削除、etcd member操作、restore、manifest変更、Argo sync、Secret参照はしていない。

## 証拠の取得方法と限界

- Kubernetes API GET（Node/Lease/Pod/Event/CronJob/CRD/Longhorn/Argo CD Application）。
- 許可済みSSH（TCP/22）から各CPのkubelet/kernel journalをパターン件数のみ集計。raw logは転記しない。
- monitoring namespaceのPrometheus（保持31日）に対し、CP1上のadmin kubeconfig経由でPrometheus Pod内のpromtoolを実行し、集計値のみ取得した。Prometheus ServiceはCodex Podからも、apiserver proxy経由でも到達できなかった（NetworkPolicy 8件が存在）。
- イベント単位の照合（本改訂で追加）: `etcd_server_leader_changes_seen_total`の5分増分が正のバケットを抽出し、各バケットについて3CPの`node_memory_MemAvailable_bytes`、`rate(node_vmstat_pgmajfault[5m])`、iowait、`up{job="node-exporter"}`、`kube_pod_container_status_restarts_total{container="kube-apiserver"}`、`container_memory_working_set_bytes{container="kube-apiserver"}`、`etcd_server_slow_apply_total`を、バケット終端の15分前〜10分後の窓で照合した。しきい値はMemAvailable 512MiB未満かつmajor fault 50回/秒超、apiserver再起動はカウンタ増分0.5以上、scrape欠落はnode-exporterのupが1未満または窓内サンプル数6未満とした。しきい値を変えると分類件数は変わる。この窓は終端後10分を含むため因果の向きを判別できない。本改訂2では同じ生データ（05:19 UTC取得の範囲クエリ出力。新規問い合わせなし）に対し、先行区間だけの窓を3種類（終端15分前〜5分前＝バケット開始前、終端30分前〜5分前、終端15分前〜終端）追加して再分類した。終端15分前〜終端の窓は、終端時点の`rate(...[5m])`がバケット内（leader change発生区間）を含むため「同時」であって厳密な先行ではない。
- etcd Podへのexecはetcdctl endpoint status / healthの読み取りのみ。
- 制限: audit logなし。apiserver metricsにクライアント識別子がなく、負荷源はverb/resource単位でしか見えない。CRI-Oのcontainer log上限が1MiBでetcd/apiserverのcontainer logは直近数十分〜1時間しか残らない。kernel PSI（/proc/pressure）は無効で、CPU/IO/memory stallを直接比較できない。node_exporterのscrapeが停止したバケットは「scrape欠落」として別に数え、停滞CPのMemAvailable / faultは欠落直前の値で評価した（過小評価の方向）。
- 本調査自体のGET/LIST（全Pod JSON、全CRD JSON等）もapiserver負荷になる。観測回数は最小限にしたが、ゼロではない。本改訂のPrometheus問い合わせは範囲クエリ13本のみで、Kubernetes APIへの追加GETはPrometheus Pod名の確認1回とexecに限った。

## 根本原因の整理

以下は観測事実（metrics・journal件数・API状態）と整合する解釈であり、PSI・audit log・障害時のプロセス別統計を欠くため、確度を付して記す。個別イベントの因果を機械的に証明したものではない。

1. **構造要因（確度 高）**: 3.9GiB RAM・swapなしのCPで、kube-apiserverのWSSが2GiB超に達する。kubeadm既定でapiserverにはmemory limit / requestがなく、kubeletのeviction thresholdは既定（memory.available 100Mi）で、ページキャッシュを使い切った後にしか動作しない。この構成ではMemAvailable 200〜300MiBで常時運用され、わずかなスパイクでmajor faultが急増する。これは観測事実である。
2. **leader changeの機序（確度 中）**: メモリ逼迫→ページキャッシュ追い出し→同一eMMC上のetcd WAL fsync / applyの停滞→heartbeat / proposal失敗→leader change。照合窓内では46件中42件でいずれかのCPの逼迫が観測され（窓内の相関、約7〜12倍の濃縮）、先行区間だけに限ると46件中25件（54%）で逼迫が先行する（約3〜12倍の濃縮）。残り21件は、同時または直後にのみ観測された17件（因果の向き判別不能）と、照合窓内でも未検出の4件（E分類）に分かれる。leader changeの結果として逼迫が起きる逆向きの経路（leader交代に伴うwatch再接続・relistによるapiserverメモリ増）も排除していない。相関に基づく推定で、厳密先行で支持されないのは21件（17件は方向不明、4件は未検出）。
3. **apiserver再起動（確度 高、ただし「原因ではない」という意味で）**: 同じメモリ逼迫の下でapiserverのliveness probeがタイムアウトし、kubeletがSIGKILLする。leader changeと同時に起きることもあるが（22/46）、必要条件ではない。再起動後のメモリ解放はシステムが「自然回復」する主要経路になっている。
4. **増幅要因（確度 中）**: etcd dataとrootfs（バイナリ・ライブラリ）が同一eMMC上にあり、major faultの読み戻しとWAL fsyncが同じデバイスで競合する。CP1は他2台よりfsyncが約3倍遅い。
5. **恒常負荷（確度 中）**: CRDへのServer-Side Apply約45回/分とCRD GET約90回/分、Argo CD Application PATCH約49回/分、Calico policy LIST群が、apiserverのwatch cache / 変換バッファのメモリを高止まりさせている。
6. **09-29以降の悪化トリガー（確度 中〜低）**: 同時期にTask Board agentのCPU使用（API観測）が約5〜8倍、WATCH開始とpods LISTが増加し、429が07時台に集中して発生した。クライアント別のaudit logがないため、「どのクライアントの要求が引き金か」は断定しない。

## 復旧・再開の安全条件（提案、未実施）

以下は提案であり、本runでは何も変更していない。実施にはユーザーの明示指示が必要で、各項目は対象・影響・停止条件・rollbackを別途記録したうえで1台ずつ行う。

1. **apiserverのメモリ圧迫を下げる**（効果 大、リスク 中）。候補: kube-apiserverの`--watch-cache-sizes` / `--default-watch-cache-size`縮小、`--target-ram-mb`の明示、またはstatic Pod manifestへのmemory requestsとkubelet `systemReserved` / `evictionHard`の引き上げ。manifest変更はkubeadm管理ファイルの直接編集になるため、Ansible role経由で管理し、1 CPずつ適用して1時間観測する。効果の判定指標はleader change件数とMemAvailable日最小で、apiserver再起動件数は副次指標とする。
2. **恒常負荷の削減**（効果 中、リスク 低）。Argo CDのCRDを含むApplicationの再同期間隔延長またはServer-Side Diff / Apply対象の見直し、Calico policy LISTの発生源確認、TiDB / PD CrashLoopの停止または隔離。いずれもcontrol-planeの外側の変更で、rollbackが容易。
3. **観測負荷の抑制**（即時、リスクなし）。Task Board agentやRCA観測での全namespace Pod / 全CRD JSON取得を避け、必要なら`kubectl get --raw /metrics`やPrometheusの集計値を使う。本RCAも同じ制約を次回から適用する。
4. **追加観測の提案**（リスク低）。kernel PSI（`psi=1`）の有効化はreboot前提のため本RCAでは実施しない。代替として、node-exporterの既存metricsでMemAvailable・major fault・etcd slow applyを1分粒度で見るアラート、またはleader change発生時のCPごとの逼迫有無を自動記録する軽量ルールをPrometheus Ruleとして追加すれば、E分類4件の未説明要因を次回切り分けられる。
5. **swap / zramの有無の確認**（効果 中、リスク 低〜中）。Armbianのzramデバイスが3つ存在するがswapは0。kubeletのswap設定との整合を確認したうえで、少量のzram swapが回収停滞を緩和するかを別途検討する。kubelet既定（NoSwap）との組み合わせ検討が必要で、本RCAでは推奨しない。
6. **Kubernetes 1.36 patch更新の再開条件**。上記1または2の実施後に、leader change 0〜1回/日、apiserver再起動0回/日、MemAvailable日最小500MiB以上が連続3日以上続いたことをPrometheusで確認する。現状（当日leader change 2窓・apiserver再起動3件、2〜4時間おき）ではdrain / 再起動を含む更新手順の最中にcontrol-plane停滞が重なる確率が高く、再開を推奨しない。
7. **残骸Podの削除**（任意、リスクなし）。default namespaceの`node-debugger-*` 5件はPhase=Failedで無害だが、明示指示があれば削除する。
