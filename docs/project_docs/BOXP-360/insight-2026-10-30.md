## 4. 本票自身の実例を回帰 eval にした

`tools/insight-test.sh` (CI の test.sh から実行) が、本文なしの summary.edn だけで次を固定ケースとして検査する。

- gate 失敗が 12 回続くと、10 回目の run でレビュー反復ループとして検出する。gate 情報のない retry はループに数えず、系列を区切る。
- 履歴の先頭 run が review-fix でも v1 で review_fix (agent-system) として数える。
- 後続 run が未開始の最新 gate 失敗も内部再作業に数え、`pending` として別に示す。gate 失敗の次の run が review-fix でも v1 では gate_rework とし、`transitions.v1.gate_rework = gate-rework.total - gate-rework.pending` (= `followed`) が常に成り立つ。 ただし Owner に見える是正 task (`v1-owner-visible-tasks` / `v1-owner-visible-agent-system-tasks`) は遷移分類とは別に「review-fix run がある task」で数えるので、gate 失敗直後の review-fix も漏れない (この snapshot では値は変わらない)。
- 時刻だけの snapshot 上限 (例 `20261030T065040Z`) は同じ秒に開始した run を含める。
- groom→implement を是正に数えない。
- 中断・blocked からの再開を是正に数えない。
- Review 後の再開は原因 unknown のまま残し、review-fix とは分ける。
- snapshot 上限より後の run を使わない。

**効果の見積もり (固定データ):** BOXP-360 の最初のループは 2026-10-29 02:13 に始まり、検出器は 10 回目の 02:50 に発火する。Owner が反復過多を指摘したのは 05:15 で、そこまでにさらに 40 回再作業していた。runner のレビュー回数上限は本文 hash ごとにリセットされ、ticket / PR 単位の累積上限がない (review-convergence.md)。この検出器の判定を runner の停止条件や dashboard の警告に使えば、約 2.4 時間・約 40 run を早く止められた可能性がある。ただし runner の停止条件を変える修正は別 scope として扱う。

## 5. 改善候補 (優先順)

1. **レビュー反復ループの早期停止** (効果が最大): gate 失敗が ticket / PR 単位で累積 10 回に達したら自動再試行を止め、残指摘を必須 / 将来改善 / nit に分ける判断を返す。runner 修正は別票で扱う (Owner 判断)。それまでは本 report の `review-loops` を週次で確認する。
2. **dashboard / 公開 SLI を v1 へ移す**: 定義 version を `correction-rules/v1` に上げ、内部再作業 (gate_rework) と Owner に見える是正を別系列にする。v0 系列は比較のため残す。
3. **Review 停止の検出**: Review で止まったまま監督や Owner の催促 note が付いた件を、note の source タグ (`kohako-supervisor` / `hermes-agent`) と時刻だけで数える。本文は読まない。Owner 救援率の部分観測にする。
4. 残る既承認改善: Ready 遷移時刻の event、Hermes ledger の集計入力への連結、dashboard の partial 表示。
